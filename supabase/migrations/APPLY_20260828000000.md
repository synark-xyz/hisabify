# Apply the stale-pro-mirror fix to production

`supabase db push` **cannot** be used for this. It would try to apply 15 pending
migrations, and the remote database has drifted from the repo:

- `account_types` and `debts` already exist in production, but their migrations are
  recorded as unapplied. `20260406000002_add_account_types.sql` uses a bare
  `CREATE TABLE`, so it aborts with "already exists".
- `20260402000001_seed_category_hierarchy.sql` has 20 plain `INSERT`s and would
  duplicate every seeded category.
- Two remote migrations (`20260729034303`, `20260729065237`) have no local file.

A push would fail partway through with production already partly mutated. Repairing that
history is a separate job, and it is not needed to fix the two stale rows.

## Option A — scripted (one command)

With the database connection string from
*Project Settings → Database → Connection string (URI)*:

```bash
npm i -D postgres   # once, if not already present
SUPABASE_DB_URL='postgresql://postgres:<pw>@db.<ref>.supabase.co:5432/postgres' \
  npm run migration:apply -- --dry-run   # preview, changes nothing
SUPABASE_DB_URL='...' npm run migration:apply
```

It previews the matched rows, refuses to continue if nothing matched, applies the UPDATE and
the `schema_migrations` row in one transaction, and prints exactly what changed.

## Option B — by hand

Supabase SQL Editor → new query. Run **step 1 first** and read the result.

### Step 1 — preview (read-only, changes nothing)

```sql
SELECT user_id, email, subscription_type, subscription_status
FROM public.users
WHERE lower(btrim(email)) IN ('coxshebatech@gmail.com', 'sam103043@gmail.com');
```

Expect the two rows at `pro` / `active`. If it returns 0 rows, stop: the addresses differ
from what is in the table, and the UPDATE below would silently do nothing.

### Step 2 — apply

```sql
UPDATE public.users
SET subscription_type = 'base',
    subscription_status = 'inactive',
    updated_at = NOW()
WHERE lower(btrim(email)) IN ('coxshebatech@gmail.com', 'sam103043@gmail.com')
  AND subscription_type = 'pro'
RETURNING user_id, email, subscription_type, subscription_status;
```

`RETURNING` prints exactly what changed. Expect 2 rows, now `base` / `inactive`.
Re-running is safe: `AND subscription_type = 'pro'` makes it match nothing the second time.

### Step 3 — record it as applied

So a future `db push` (after the history is repaired) does not try to re-run it:

```sql
INSERT INTO supabase_migrations.schema_migrations (version, name)
VALUES ('20260828000000', 'reset_stale_pro_mirror')
ON CONFLICT (version) DO NOTHING;
```

## Why this is safe

`npm run verify:migration` executes the exact SQL from
`supabase/migrations/20260828000000_reset_stale_pro_mirror.sql` against a throwaway
database carrying the real `CHECK (subscription_type IN ('base','pro'))`, and asserts it:

- downgrades both target rows,
- leaves an unrelated paying customer and an already-free user untouched,
- is idempotent on re-run,
- matches `lower(btrim(email))`, so a differently cased address is not silently skipped.

## Why the agent could not run it

The only credential on this machine is `VITE_SUPABASE_PUBLISHABLE_KEY` (anon). RLS on
`public.users` restricts UPDATE to `auth.uid() = user_id`, so an anon PATCH returns HTTP 204
with an empty `RETURNING` body: zero rows affected. Verified, and nothing was modified.
Applying this needs the service role key or a dashboard session.
