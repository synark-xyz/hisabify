# Apply the storage fixes to production

The client fix is already in the app. The upload will keep failing until this SQL runs,
because the failure is server-side.

`supabase db push` is **not** safe here: the remote database has drifted from the repo, so a
push would try ~17 pending migrations and fail partway with production already mutated. See
`APPLY_20260828000000.md` for the details of that drift.

Run this by hand instead. Supabase dashboard -> SQL Editor -> new query.

## What has been verified, and what has not

**Verified against real Supabase Storage.** A local stack (`supabase start`, storage-api
v1.70.3) was seeded into production's exact state — `avatars` bucket present, zero policies on
`storage.objects` — and reproduced the reported failure byte for byte through the real
Storage HTTP API:

```
POST /storage/v1/object/avatars/<uid>/1.png
403 {"message":"new row violates row-level security policy","code":"AccessDenied"}
```

Applying `20260831000000` there, the same upload returns `200 {"Key":"avatars/<uid>/1.png"}`,
the public URL fetches `HTTP 200`, and an upload into another user's folder is still refused.
The app's own code path was then exercised through `@supabase/supabase-js` (the sequence in
`PersonalPage.handleAvatarUpload`: `getSession` -> `upload` with `contentType` -> `getPublicUrl` -> fetch), which passes. Dropping the INSERT policy makes that same client
reproduce the user-visible error again, and restoring it fixes it — so the migration is the
cause of the fix, not a coincidence.

`20260831000001` was verified the same way: `feedback-attachments` and `support-attachments`
return `NoSuchBucket` beforehand; afterwards feedback uploads succeed while its public URL
correctly 400s (private), support uploads succeed and read back `HTTP 200` (public), a
signed-out upload to `anonymous/` succeeds as `SupportPage` requires, and cross-user uploads
are denied. Both migrations were re-run to confirm they are no-ops.

`npm run verify:storage-policies` additionally asserts 30 policy-level behaviours against a
real Postgres, including that the harness's own `storage.foldername` matches Supabase's
upstream definition.

**Not verified.** That *your* production project is fixed. Everything above ran against a
local Supabase instance; applying the SQL to the hosted project needs a credential this
workspace does not have. Step 3 below is that final check, and it is still outstanding.

## Step 1 — see what is actually there (read-only)

```sql
SELECT id, public FROM storage.buckets WHERE id = 'avatars';

SELECT policyname, cmd, qual, with_check
FROM pg_policies
WHERE schemaname = 'storage' AND tablename = 'objects'
ORDER BY policyname;
```

Expect the bucket to exist. The observed failure is that no INSERT policy for `bucket_id =
'avatars'` is listed, so RLS rejects every upload with
`new row violates row-level security policy`.

## Step 2 — apply

Paste the whole of `20260831000000_fix_avatar_storage_policies.sql` and run it. It is
idempotent (`ON CONFLICT`, `DROP POLICY IF EXISTS`), so it is safe to re-run.

## Step 3 — verify

Re-run the Step 1 policy query. You should now see four `avatars` policies: public SELECT,
plus INSERT/UPDATE/DELETE restricted to `auth.uid()::text = (storage.foldername(name))[1]`.

Then in the app: Profile -> Personal Info -> camera button on the avatar. It should upload
and the new image should render immediately, in-app and in the header.

## Step 4 — record it so a future push skips it

```sql
INSERT INTO supabase_migrations.schema_migrations (version, name)
VALUES ('20260831000000', 'fix_avatar_storage_policies')
ON CONFLICT (version) DO NOTHING;
```

## Step 5 — the other missing buckets

The same probe showed `feedback-attachments` and `support-attachments` do not exist in
production either, so in-app feedback screenshots and support attachments fail the same way.
`20260831000001_restore_missing_storage_buckets.sql` fixes both. Apply it the same way, in
the same session, then record it:

```sql
INSERT INTO supabase_migrations.schema_migrations (version, name)
VALUES ('20260831000001', 'restore_missing_storage_buckets')
ON CONFLICT (version) DO NOTHING;
```

Verify: Profile -> Support should send with an attachment, and the in-app feedback form
should accept a screenshot.

`receipts` is also absent, but deliberately left that way: receipt images are stored inline
as data URLs in `transactions.receipt_url`, so nothing writes to that bucket.

## Unrelated blocker found while verifying

`supabase start` cannot bring the repo up from scratch. `20260310000000_ensure_all_categories.sql`
uses `ON CONFLICT (name)` at line 20, but only adds `categories_name_key UNIQUE (name)` at
line 62, so a fresh database aborts with:

```
ERROR: there is no unique or exclusion constraint matching the ON CONFLICT specification (SQLSTATE 42P10)
```

Production is unaffected (the constraint already exists there), which is why this has gone
unnoticed. It does block local development and CI-from-scratch. Left alone here because it is
unrelated to the storage fix and reordering a shipped migration deserves its own change.
