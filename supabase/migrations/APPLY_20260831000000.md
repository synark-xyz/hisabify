# Apply the storage fixes to production

The client fix is already in the app. The upload will keep failing until this SQL runs,
because the failure is server-side.

`supabase db push` is **not** safe here: the remote database has drifted from the repo, so a
push would try ~17 pending migrations and fail partway with production already mutated. See
`APPLY_20260828000000.md` for the details of that drift.

Run this by hand instead. Supabase dashboard -> SQL Editor -> new query.

## What has been verified, and what has not

**Verified.** `npm run verify:storage-policies` runs both migrations verbatim against a real
Postgres (PGlite) on a reconstructed `storage` schema and asserts 26 behaviours: that an
upload is denied before the fix (reproducing the production symptom), that a user's own
folder is allowed afterwards, that another user's folder / the bucket root / an
unauthenticated request are all denied, that the exact path shape the app builds is accepted,
that the bucket ends up public and readable, that re-running is a no-op, that a
drifted-to-private bucket is repaired, that unrelated bucket policies survive, that the feedback bucket stays private while the
support bucket is public, and that signed-out support uploads land in `anonymous/`. Dropping
the INSERT policy flips the allow case back to denied, so it is checking behaviour rather
than passing vacuously.

**Not verified.** That production is fixed. PGlite is a stand-in, not Supabase Storage, and
applying the SQL requires a credential this workspace does not have. Anonymous signup against
the project is also rate-limited, so no authenticated end-to-end upload could be attempted.
Step 3 below is the acceptance check, and it is still outstanding.

## Step 1 — see what is actually there (read-only)

```sql
SELECT id, public FROM storage.buckets WHERE id = 'avatars';

SELECT policyname, cmd, qual, with_check
FROM pg_policies
WHERE schemaname = 'storage' AND tablename = 'objects'
ORDER BY policyname;
```

Expect the bucket to exist. The observed failure is that no INSERT policy for `bucket_id =
'avatars'` is listed, so RLS rejects every upload with
`new row violates row-level security policy`.

## Step 2 — apply

Paste the whole of `20260831000000_fix_avatar_storage_policies.sql` and run it. It is
idempotent (`ON CONFLICT`, `DROP POLICY IF EXISTS`), so it is safe to re-run.

## Step 3 — verify

Re-run the Step 1 policy query. You should now see four `avatars` policies: public SELECT,
plus INSERT/UPDATE/DELETE restricted to `auth.uid()::text = (storage.foldername(name))[1]`.

Then in the app: Profile -> Personal Info -> camera button on the avatar. It should upload
and the new image should render immediately, in-app and in the header.

## Step 4 — record it so a future push skips it

```sql
INSERT INTO supabase_migrations.schema_migrations (version, name)
VALUES ('20260831000000', 'fix_avatar_storage_policies')
ON CONFLICT (version) DO NOTHING;
```

## Step 5 — the other missing buckets

The same probe showed `feedback-attachments` and `support-attachments` do not exist in
production either, so in-app feedback screenshots and support attachments fail the same way.
`20260831000001_restore_missing_storage_buckets.sql` fixes both. Apply it the same way, in
the same session, then record it:

```sql
INSERT INTO supabase_migrations.schema_migrations (version, name)
VALUES ('20260831000001', 'restore_missing_storage_buckets')
ON CONFLICT (version) DO NOTHING;
```

Verify: Profile -> Support should send with an attachment, and the in-app feedback form
should accept a screenshot.

`receipts` is also absent, but deliberately left that way: receipt images are stored inline
as data URLs in `transactions.receipt_url`, so nothing writes to that bucket.
